# CRM recovery and crew workspace — design

## Problem and outcome
The published nautical pilot hides a working CRM behind a narrow public gateway. Its replacement information panels are not the CRM the owner requested. Restore the existing CRM as the administrator workspace, with the nautical workflow added as a module. Crew must see a simple tour/calendar and ticket workflow without CRM records or money. Keep the existing listening-mode implementation. Labels describe roles, never staff names.

## Scope and owner decisions
This increment restores existing contacts, inbox, pipeline, agent, automations, lab and settings including WhatsApp configuration, and connects the existing tour operations/calendar. It simplifies the crew entry without rewriting booking, QR or movement rules. The owner authorized code coordination and isolated deployment on bambola.heili.cloud, Ubuntu1899808, preserving Hair and every other service. The source assignment is recorded in crm-recovery-ownership.json; the remote modalita-ascolto ownership overlaps remain recorded. No real data, messages, payment integration or provider credentials are introduced. The existing CRM features may show disconnected/listening states; displaying them is not activating a provider.

The affiliate backlog remains binding: automatic application, access only after approval, isolated agency records and 10% commission on collected tour revenue excluding extras. This increment states that the existing free-text agency field does not implement affiliation, and removes the unimplemented affiliate preview from the main workspace. Affiliate data/authentication and payouts require their own reviewed increment after the CRM entry is restored. Crew task assignment must select a real membership of the active organization. New assignments store assignedMemberId as an optional field in the existing JSON service record, binding the assignment to that specific membership record; assignedTo remains the legacy text field; legacy text is displayed explicitly as unverified and never grants permissions.

## Design
Use a reusable server-selected workspace profile, standard by default and marine for the dedicated boat instance. Existing standard/beauty navigation and permissions stay unchanged. In marine mode only owner/admin enter the CRM; members enter nautical operations. Membership resolved from the database remains authoritative, including active organization. A client prop controls presentation, never permission.

The administrator keeps the original AppShell and original screens. Marine navigation includes Dashboard, Contacts, Conversations, Pipeline, Agent Heili, Automations, Laboratory, Calendar and tours, Crew app, and Settings with its existing WhatsApp/Templates/Team/Listening pages. Calendar and tours uses the existing marine state owner inside the shell, with tour/calendar/administration views backed by the existing marine API; CRM navigation opens original components, never informational replacement panels. Switching a tour must retain existing request ordering and pending-mutation locks. Crew app is a separate entry on the same instance, with a visible return-to-CRM action only for an administrator.

Crew starts with tour selection/calendar and a large Scan ticket action, plus Search passenger. Food preparation and equipment services (paella, floating mattress or other labeled service records) show quantity, the verified member name for new assignments and pending/doing/done state; equipment and food use existing service records. Tour notes and the full passenger list sit in the tour-detail section, below the primary Scan ticket and Search passenger controls. Camera opening does not record boarding; confirmed movements remain explicit. Preserve manual code/name lookup, wrong-tour rejection, duplicate protection, offline uncertainty/reconciliation and pending command retry. Use the same calendar component and Caracas dates; disclose its existing 50-tour bound. No caching of passenger data or optimistic boarding. The web app gains a manifest, 192px and512px PNG icons with a plain Heili monogram and standalone launch to crew operations, without a service worker or offline claim. Physical Android installation/camera remains a separate verification, never inferred from browser emulation.

Security is enforced in the server and gateway. Every session-authenticated CRM route must reject member access in marine mode before data reads/writes; events must reject before subscription. Marine APIs retain their own role-projected payload and command guards. Anonymous public registration stays token-scoped. No broad /api/* or /api/auth/* proxy rule. Existing owner-only actions remain owner-only. Default-deny covers unknown roles. No tenant scope is accepted from a client instead of session membership.

## Alternatives and trade-offs
Rebuilding a second CRM inside the nautical dashboard duplicates working components and caused the current navigation failure; reject it. A separate crew application with its own authentication/database adds synchronization and duplicate security work; retain one instance and distinct role-checked entry points. A gateway-only role check would leave direct server calls unsafe and require another auth protocol; use the existing server session wrapper plus explicit gateway routes. Per-organization configurable product modules are a longer-term option; this dedicated instance uses a deployment profile to avoid a new schema or unsafe tenant migration. Existing multi-organization membership scoping remains intact.

## Risks and mitigations
- Data access: server profile/role checks and existing tenant filters protect CRM; gateway keeps a narrow exact inventory in crm-route-surface.md.
- Provider effects: this synthetic pilot allows reading existing configuration and local CRM changes, but all routes that send/test/sync/activate a provider are denied before proxying as specified in the route inventory. Internal app networks have no egress and no provider secrets are added. This is not an active WhatsApp connection.
- Offline/concurrency: preserve request generation, pending command and reconciliation locks; never record boarding from a scan alone.
- Calendar capacity: reuse the actual repository priority: active boarding/underway first, Caracas today next, future planned next, then other/history; completed/cancelled newest first, other starts ascending; limit50. Existing no-overlap trip rule prevents fifty simultaneous active tours on this one boat. Test60historical+current/upcoming fixtures, showing current within50; direct selected-id lookup stays org-scoped beyond summary.
- Device: manifest/mobile browser tests do not prove physical Android camera/installability.
- Deployment: old host snapshot is invalid, new reviewed snapshot/operator required; never restore shared config or Hair.
